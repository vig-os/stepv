# [PR 47](https://github.com/vig-os/stepv/pull/47) feat(view): exact section caps from the kernel, per part

Closes #43.

## What
The stencil cap (#34) is one grey for all parts. The fixture's pins interfere with the plate, so their sections are capped, but nobody can see whose is whose. Now the kernel cuts each part exactly, and the viewer caps each one in its own colour.

- **Kernel**: a `section` op in `stepv-occt --serve` (protocol in `kernel/measure.h`).
  - **Input**: the viewer's plane, `[nx, ny, nz, w]`, keeping `dot(p, n) <= w`.
  - **Output**: for each part with solids that the plane crosses, triangles in model coordinates, holes included.
  - **How**: `BRepAlgoAPI_Common` of the part's solids with a face on the plane, then `BRepMesh`. The core now links `TKBO`.
  - **Deviation from the issue**: #43 planned closed polylines plus an earcut in the viewer. The kernel already knows which loop is a hole and has a mesher, so it returns triangles, and the viewer needs no triangulator.
- **Viewer** (`src/view/{gpu,app,measuring}.rs`):
  - The query is sent once the plane has held still for 150 ms. The worker keeps only the newest section query, separately from the newest measurement pair.
  - Exact caps are drawn only for the plane they were cut by. Each is hatched in its part's colour, and the id pass draws it as "nothing".
  - The stencil cap stands in while a query is in flight, after a refusal, and for any other plane. The Section panel says "Exact section" or "Approximate section", with the reason on hover.
  - Where caps overlap, the later one is drawn a depth step nearer, so it shows cleanly. Only overlapping caps get ranks, and ranks stop at 63.

## The kernel is untrusted
- The server reads answer lines up to 16 MiB (`MAX_LINE`). A kernel that writes more is killed (`Error::TooLong`), and that also turns exact caps off.
- The caps are uploaded as an index buffer, and their total size is checked against the device's limit before anything is built. An answer that is too big is a refusal, not a wgpu panic.
- A timeout, the memory cap, or caps too big for the GPU turn exact caps off for the session. Otherwise every stop of the slider would cost a kernel restart. Other refusals last until the plane moves.

## Cost
On 900 parts (the fixture × 300, from `stress-gen`), the query took 0.27 s for 144 caps, about 2 ms a cap. It's held to the run's limits, as a measurement is.

## Review
A fresh code-reviewer agent blocked the first commit on two points:
- an unbounded kernel answer could exhaust a GPU buffer and crash the viewer;
- the depth step grew without limit as more caps were cut.

Both are fixed in `d52f8f9`, along with the nits: refusals now clear, slow models stop re-querying, parts coloured only per face get their first face's colour, the state machine is unit-tested, and the CHANGELOG wording is corrected.

One nit is declined on purpose. If one part's Boolean fails, the whole query fails and the stencil cap stays: a part left without an exact cap would look hollow.

A second fresh review of `d52f8f9` blocked on a regression: a late refusal for an older plane stopped the current plane from ever being asked. It's fixed in `bd5729a`, with a test, along with that review's nits: the 16 MiB cap, a sticky `TooLong` error, the size check before building, and freeing the reader's buffer.

A third fresh review approved `bd5729a`, with nits. `85061b3` fixes them: the reader now sends a typed `Line::TooLong`, not a string sentinel a kernel could forge, so an over-long ready line is `TooLong` too, and the error text no longer says the kernel restarted.

Review commits `75fbed0`, `d52f8f9`, `bd5729a` and `85061b3`.
