# [PR 59](https://github.com/vig-os/stepv/pull/59) feat(kernel): stream a run's outline and progress before its summary

## Description

The second step of #54: the event stream that a front-end shows while it waits. `stepv-occt --stream` replaces a run's one JSON summary line with a sequence of frames:

1. a STEP file's **outline**, as soon as the file is parsed;
2. **progress** through the transfer and the meshing;
3. the **summary**, which is always the last frame.

The outline comes from the run's own reader, so the file is parsed only once.

**The frame format** (`kernel/stepv_occt.h`): `SVEV`, then a kind byte, then a little-endian u32 length, then the payload. Each payload is one JSON object today. Kinds 4 and up are reserved for the per-part boxes and meshes in P1, which will be binary payloads rather than base64.

**Measured on Ultimaker 3:**

- The tree arrives at **4.3 s**; the summary arrives at 101 s, in 101 frames.
- Transfer progress reaches 15.6% by 15 s, then **doesn't move for 80 s**. OCCT's own indicator doesn't advance inside one solid's healing, and solid 221's p-curve projection is that 80 s (#51).
- So progress shows where the time goes, but it can't make that wait shorter. The per-face healing budget in step 3 is what will.

## Changes Made

- **`kernel/stepv_occt.h`:**
  - the event kinds;
  - the callback type;
  - `stepv_occt_run_stream`. `stepv_occt_run_ex` is now that call with no callback.
- **`kernel/stepv-occt-core.cpp`:**
  - an `Events` sink. It limits progress to one event per stage every 50 ms, besides the first and the last, and never steps back.
  - a `Message_ProgressIndicator` that reports transfer progress in thousandths. It's used for both STEP and IGES.
  - mesh progress counts two passes over the prototypes.
  - the outline is sent between the parse and the transfer. If the outline fails, it's left out and the run goes on.
- **`kernel/outline.{h,cpp}`:** `outline_json(STEPControl_Reader&)` works on a reader that has already parsed the file.
- **`kernel/stepv-occt.cpp`:**
  - `--stream`, whose callback writes the frames. The `DONE` frame carries the summary with `sandbox`, the same as the plain line.
  - `--stream` is refused alongside `--serve` or `--outline`.
  - the `STEPV_OCCT_TEST_STALL_MS` test hook holds the run once the outline is out.
- **`src/occt.rs`:**
  - `Event`, `Progress`, `Stage` and `StreamError`.
  - `read_events`. It refuses frames over 64 MiB on the header alone, and rejects a bad magic, an unknown kind, a bad payload, trailing bytes, and a stream with no summary.
  - `run_streaming`. Decoding happens on the reader thread, which passes events over a bounded channel to the caller's thread. Progress events are dropped when the caller falls behind; the outline never is.
  - A kill (wall clock or memory cap) keeps the events that arrived and has **no summary**. A kernel that exits with a broken stream counts as `Crashed`.
  - `supervise()` now takes the stdout reader and a tick, and `run`, `run_streaming` and `outline` all use it.
- **`tests/stream.rs`** (6 tests):
  - the outline comes first and equals `--outline`;
  - progress is monotonic and every stage finishes;
  - the summary and mesh match a plain run;
  - IGES and BREP send no tree;
  - a clean failure still streams its summary;
  - a kill after the outline keeps the outline and has no summary;
  - six fake kernels (shell scripts) produce broken streams, and each counts as a crash;
  - the flag conflicts are refused.
- **Unit tests for the decoder:** every truncation point, and each rejection.
- **Docs:** CHANGELOG, and plan.md "Events and progress (#54, step 2)".
