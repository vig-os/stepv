# [PR 113](https://github.com/vig-os/stepv/pull/113) fix(ql-e2e): order the supervisor tests on logged events, not a first event (#111)

## Fix #111: the supervisor tests wait on the service's own logged events, and tell runs apart by identity

Fixes #111.

### Root cause (#111)
A 1.5 s run was killed before its first event, with admission limit 1 on the runner. #108 round 2 had replaced a sleep with "wait for the run's first event" as the sign that its kernel was running. The slow run's deadline is 1.5 s, and on CI's slower runner its TREE didn't arrive before the kill (`deadline: 1 run #4 … killed at 1509 ms`, then the wait ran out at `up 20440 ms`). The handover case, with a 2 s deadline, had the same flaw. This is a test bug.

### A separate bug, introduced by this PR's own earlier commits
When 9a6ac31 removed the `sleep 1`, the harness's whole-second log windows began to catch the lines of the step before.
- 9a6ac31 counted `6 kernel spawns, expected 10`, waiting on the wrong service instance.
- cd30216 failed ql-e2e's cache control on the previous request's line.
- d4efd38 narrowed the windows to the microsecond. That still tells runs apart by time, so this round replaces it with identity.

### Fix
- **Waiting on the logged event, not on time.** The probe asks `supervisor.sh`, on stdout, to wait for a run's logged spawn, queueing or held-deadline (`await <what> <run> <pid>`), and goes on once that exact line is there.
- **Identity, not time windows.** When the service takes a run, it now sends the client `accepted(run)` with the run's number in its log. The client then has the service's pid as well (`StepvSupervisorRun.onAccepted`, `servicePid`). `processIdentifier` stays 0 until a message from the service arrives, so it can't stand alone.
  - `drive` matches exactly that run of that service, and every log check is scoped to the service pid its probe reported.
  - `set_start` only bounds how much log is read.
  - A self-check plants a decoy line from another service: a pattern that ignores the pid fails it.
  - ql-e2e's cache control asks the second time through a hard link (same inode, new path), and the verdict goes by path.
- **The held handover is released by the test, not by elapsed time.** A test build (`STEPV_TEST_HOOKS`, `admission-hold`) holds each admitted run until `release-N` appears in the service's tmp. It logs when the run's deadline passes while held, and the probe releases the run only after seeing that line. The run then reaches the admission-time check past its deadline and is refused, never spawned. The earlier widenings are reverted (deadline 2 s, drive 60 s, wait 15 s). This also resolves #109's first item.
- **The fix for the real cause stays.** The deadline kill needs no "running" precondition. At L ≥ 2 it is also tested beside a running run (killed at 1.5 s while the held run goes on). At L = 1 no two kernels run at once, so the kill alone is the case there. Runs that must hold a slot while an order is checked use a 4000-part file and are cancelled by the probe.

### Round 4: ql-e2e judged by identity, from one log stream (dcabac0, 37de33d)
- **Root cause of the ql-e2e red** (run 38405706989): the extension's lines *were* logged — the failure dump showed `thumbnail <the request's own path>: drawn` stamped 13:57:15.076 — but stamped before the request's own start, taken earlier by the wall clock. On CI's macOS VM a log event's timestamp runs behind `date` (an estimated ~0.7 s), so every window opened at a wall-clock instant (`log show --start`, or e2elog's microsecond `since`) dropped the request's own line, and a 769 ms thumbnail was judged cached. Not log lag: polling longer could not find it.
- **Fix:** `run-all.sh` starts one `log stream` before the first request (`QL_E2E_STREAM`), read by `ql-e2e.sh` and `supervisor.sh`; no `log show` anywhere. A request's lines are found by its own path, the supervisor's by service pid and run number; no time is compared (`e2elog.py`). Every wait is bounded (30 s) and says so when reached.
- **37de33d:** c71e629's probe signalled `taken` after `done`, so a refused run's temporary probe could be freed first: `swift_abortRetainUnowned` on sage (L = 4). `done` is now signalled last.
- **Results (sage):** `just macos-test` exit 0; `scripts/ql-e2e/supervisor.sh` exit 0; `just ql-e2e` exit 0, ALL PASS.
- **Cache control stays honest:** with the cache defeat removed (each request a hard link to the source: same inode), `run-all.sh` exits 1 once the inodes are in Quick Look's cache: all three thumbnails `QL served a cached thumbnail` (8–9 ms), VERDICT FAIL.
