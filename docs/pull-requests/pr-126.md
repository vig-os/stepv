# [PR 126](https://github.com/vig-os/stepv/pull/126) feat(cap): stepv-cap, the kernel memory cap wrapper (83a (i))

## What
The first of #83's three PRs (83a), part (i): the `stepv-cap` wrapper, the CLI's reuse of its sampler, and the balloon proof.

- **`src/cap.rs` (`stepv::cap`):** the CLI's footprint sampler moved out of `src/occt.rs`. That is `footprint` (macOS phys footprint, Linux RSS), `tree_footprint` (a process and its descendants by parent chain), and `Sampler` (polls every 5 ms and keeps the peak). It is deliberately not `RLIMIT_AS`; the reasons are on `occt::Limits`. The CLI's `supervise` now uses `Sampler` with the same timing and the same single-process measure, so its behaviour is unchanged. `occt::footprint` stays, re-exported.
- **`src/bin/stepv-cap.rs`:** `stepv-cap --memory-mb N [--label NAME] [--report-json PATH] -- CMD...`
  - It runs `CMD` in its own process group and caps the summed footprint of `CMD` and its descendants by parent chain.
  - Past the cap, it kills the group and the descendants it counted, prints one stderr line naming the label, the cap and the peak, and exits **86** (`stepv::cap::EXIT_OVER_CAP`).
  - Otherwise it exits as `CMD` did, by code or by the same signal. `125`–`127` are stepv-cap's own failures, as `timeout(1)` has them.
  - SIGINT, SIGTERM, SIGHUP and SIGQUIT are passed on to the group. `CMD` sees its cap in `STEPV_CAP_MB`.
  - `--report-json` writes `label`, `cap_bytes`, `peak_bytes`, `wall_ms`, `over_cap`, `code` and `signal`, for 83b.
  - Documented in the binary's rustdoc and in CHANGELOG.
- **`tests/cap.rs`:**
  - The balloon proof: the kernel's `STEPV_OCCT_TEST_BALLOON_MB` hook, run under a 64 MiB cap, is killed in under 4 s, exits 86, and the stderr line names it. It is also caught when a shell starts the kernel.
  - Exit codes and signals pass through, and the report fields are checked.
  - A ballooning test, run under the wrapper the way a test runner would run it, fails with its test name.
  - The existing CLI cap tests (`tests/cli.rs` `memory_cap_exits_3`, the measure server's balloon in `tests/measure.rs`) are untouched and pass.

## Limits (filed, `chore`, after the owner's MVP-first ruling)
- A process that is reparented (its parent exits) or leaves the group escapes the cap, and may outlive stepv-cap: #128.
- The Linux footprint is statm RSS × 4096, not `smaps_rollup` PSS: #129.
- Signal forwarding keeps only the last of two quick signals, and has no test: #130.
- `measure.rs` shares only `footprint`, not `Sampler`: #131.
- Exit 86 is ambiguous with a `CMD` that exits 86; only `--report-json`'s `over_cap` tells them apart. `CMD` runs in a background process group, so an interactive command reading the terminal gets SIGTTIN.
- The `ql-e2e` failure on the first macOS run is #127 (Quick Look, untouched here).

## Where the balloon proof runs in CI
`tests/cap.rs` runs in **Kernel (macos-15)** and **Kernel (ubuntu-26.04)**, step `nix flake check` (the `nextest` check). It also runs in the **Tests** job, `just test` (`cargo test --workspace`).

## Next: 83a (ii), not built here
- **Routing:**
  - The harness gets a default cap.
  - `corpus-diff.py` moves into `scripts/`, runs each kernel under stepv-cap, and gets a workers × cap ≤ host-budget default.
  - `scripts/test-macos.sh`'s direct kernel calls go through stepv-cap.
  - So do `occt-patch-check`, in `tests/occt_patch.rs` and in the nix `occt-patch-reference` check.
- **Per-test cap (decided):**
  - Every kernel launch from a test goes through a `capped(label, …)` helper, `stepv-cap --label <test name>`, so a breach fails that test by name.
  - The test run as a whole is wrapped in one aggregate `stepv-cap --label <suite>`, the backstop against wedging the host.
  - nextest `test-threads` is set in `.config/nextest.toml` so that threads × per-kernel cap ≤ a documented host budget.
  - The wrapper's path resolves through one helper that both `just test` and the nix check use (an env var set by both, falling back to `CARGO_BIN_EXE_stepv-cap`).
  - It does not depend on nextest's experimental wrapper scripts; adopting them is #125.
- **The lint:** a CI lint rejects uncapped kernel launches, with a test that plants one.
