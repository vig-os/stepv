# [PR 116](https://github.com/vig-os/stepv/pull/116) fix(ci): keep the viewer job's Xvfb up between clients (-noreset)

## Description

Fixes #104. The Viewer (Linux, lavapipe) job's window tests intermittently failed with `winit EventLoopError … Failed to open connection to X server`.

**Root cause:** Xvfb was started by `xvfb-run` without `-noreset`. An X server *resets* whenever its last client disconnects, and a connection that arrives during the reset is dropped. `scripts/test-window-tests.sh` runs the 14 window tests in parallel under one `xvfb-run`, and each `stepv view` is its own short-lived client. When all the running clients had closed at the same moment that another test's stepv connected, winit's `XOpenDisplay` failed. The GPU viewer then fell back to software for the wrong reason, and the test's note assertion (tests/cache.rs:1034) failed.

**Ruled out:**
- *Start race:* `xvfb-run` starts the command only after Xvfb signals readiness (SIGUSR1). Each failure was mid-suite, about 21 s in, after other tests had already connected.
- *Server dying:* the same server served the software fallback in the same test, which drew and passed.
- *Connection limit:* there are at most 4 clients at once, against Xvfb's 256.
- *Display shared with another server:* there is one `xvfb-run -a` per step, run in sequence.
- *#84 watchdog:* it kills the kernel only, never X.

**Occurrences (kernel.yml run history):** 38337928702 (#103), 38362262033 (#98), 38377606897 (main push), 38378915656, 38848855133. Each time it was the same test and the same error.

## Changes Made

- `scripts/test-linux-viewer.sh`: one `xvfb <size> <cmd>` helper, `xvfb-run -a -s "-screen 0 <size>x24 -noreset"`, used for all three Xvfb steps (window tests, `test-viewer.sh`, no-GPU fallback). There are no sleeps, retries or skips.

## Demonstration

These ran on Linux x86_64 (vm-dev), in CI's own container (`test-linux-viewer.sh`'s Debian trixie image and env). stepv was built once, then CI's window-test step was looped: `xvfb-run -a -s "<args>" scripts/test-window-tests.sh -q --release`.

| Xvfb args | runs | pass | X-server failures |
|---|---|---|---|
| `-screen 0 1600x1000x24` (main) | 40 | 39 | **1**: run 38, `a_gpu_that_refuses_the_pipelines_falls_back_to_software`, `Failed to open connection to X server`, tests/cache.rs:1034, the same failure as CI |
| `… -noreset` (this PR) | 120 | 118 | **0** |

Neither of the 2 non-X failures after the fix was an X error.
- One was observed as `Text file busy (os error 26)` (`closing_the_viewer_mid_load_cancels_the_kernel`, tests/cache.rs:992), from the tests' `script()` helper. That race has a different root cause and is filed as #117.
- The other (`a_viewer_with_no_cache_leaves_no_artifact`, tests/cache.rs:862) failed on an exit-code/status mismatch, but its output wasn't kept. It is only **inferred** to be the same ETXTBSY race, because that test also execs a `script()` kernel.

**The reset, deterministically:** one client sets a root-window property and disconnects, then a new client reads it back.
- Default: `STEPV_104: no such atom on any window.` The server reset when its only client left.
- `-noreset`: `STEPV_104(STRING) = "still-here"`.

**Connections dropped during a reset:** 3 workers each opening and closing `xdpyinfo` in a loop, 5 × 3000 connections. With the default server, 3 were refused (`unable to open display ":99"`); with `-noreset`, 0.

The Viewer (Linux, lavapipe) job passed on this PR.
