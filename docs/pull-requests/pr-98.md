# [PR 98](https://github.com/vig-os/stepv/pull/98) feat(macos): run the kernel under an XPC supervisor service in each extension (#64 part 1)

## #64 part 1: the XPC supervisor service, bundled and probed

Refs #64. Part 2 switches both extensions onto the service and `Closes #64`.

### What changes
- **`StepvSupervisor.xpc` in each appex** (`macos/Supervisor/main.swift`, protocol and client in `macos/Shared/StepvSupervisor.swift`):
  - The service spawns its own `Contents/Helpers/stepv-occt /dev/fd/3 --format … --stream --mesh …`, with the file's descriptor passed over XPC.
  - It forwards TREE and PROGRESS, then replies with the summary and the mesh, which it hands back as an unlinked file.
  - It kills the kernel when the connection goes (cancel), at the deadline, or past the memory cap.
- **Bundling:** each `.xpc` has its own OCCT closure (31 dylibs, 51 MB). The service's sandbox blocks dyld from opening the app's shared `Contents/Frameworks` ("file system sandbox blocked open()").
- **Signing:**
  - The kernel is signed `app-sandbox` + `inherit`, the service `app-sandbox` alone.
  - Signing is ad-hoc with no hardened runtime; Developer ID is #97.
  - `codesign --verify --deep --strict` passes.
- **The SVEV reader in Swift** (`macos/Shared/StepvFrames.swift`) has `read_events`' framing bounds.
- **ql-e2e in the repo** (`scripts/ql-e2e/`, `just ql-e2e`):
  - Quick Look itself runs the installed extensions (`QLThumbnailGenerator`, a `QLPreviewView` host), and their own log lines are the verdict.
  - A sandboxed probe placed in a copy of the built appex drives the real service. `test-macos.sh` runs the probe too.

### Findings on the way
- **fd 3:** XPC hands the descriptor over as the lowest free fd, often 3. `adddup2(3,3)` doesn't survive `POSIX_SPAWN_CLOEXEC_DEFAULT`, so the kernel's `dup(stdout)` landed on fd 3 and the read failed with "Illegal seek". The service now moves the descriptor to fd 10 or higher first.
- **Memory cap:** `proc_pid_rusage` on the child is EPERM in the sandbox, so the cap uses `PROC_PIDTASKINFO` resident size. The trade-off is documented in plan.md.
- **Stale extension processes:** an extension process left running from an older install keeps serving Quick Look's requests. ql-e2e refuses to run while one exists.

### Tests (sage, macOS 26.4)
- `scripts/test-macos.sh`: exit 0.
  - Frames: a real stream in 1-, 7-, 9- and 4096-byte chunks, and every broken stream. Dropping the MAX_FRAME guard or the trailing-bytes check fails the tests.
  - Layout and entitlements are checked.
  - The supervisor probe passes 12 of 12:
    - STEP (TREE first, `macos-outer`), IGES and BREP;
    - a deadline kill at 1.5 s, reaped in about 8 ms, while a concurrent run finishes in about 65 ms;
    - the next run right after the kill in about 65 ms;
    - the memory cap;
    - cancel (signal 9, reaped about 4.5 ms after the cancel);
    - a refused format;
    - all 8 kernels gone.
- `scripts/ql-e2e/run-all.sh`: exit 0, ALL PASS (thumbnail and preview for STEP, IGES and BREP, plus the probe).
- CI: the new "Quick Look end to end" step tries `just ql-e2e` in the runner's session. If the runner can't register extensions, it becomes a documented local gate with an issue.
- No Rust or kernel changes.
