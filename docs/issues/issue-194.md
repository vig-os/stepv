# [Issue 194]: [ADR-0002: OCCT out of the runtime: a Rust-only STEP→mesh pipeline, OCCT kept as the test oracle](https://github.com/vig-os/stepv/issues/194)

## Motivation
Owner decision (2026-11-15, on #170): the goal is 100% Rust with rayon and SIMD, so stepv gets lighter and stops depending on OCCT. Today OCCT does more than meshing, and each of its jobs needs a Rust owner before OCCT can leave the runtime binary.

## What OCCT does today, and who takes each job over
| Job | Today | Rust owner |
|---|---|---|
| STEP parse and product structure | OCCT transfer (kernel) | **done:** graph core G1–G3 |
| Bounding boxes and placeholders | OCCT | **done:** G4, G6a–c |
| Colours (XCAF) | OCCT | G7 #141 |
| Analytic faces and edges | OCCT | M1a–M4a #142–#146 |
| Swept surfaces | OCCT | #171 |
| B-spline surfaces | OCCT | #172 |
| Mixed products, face by face | OCCT | #170 (the transition) |
| Healing (sewing, tolerance repair, `kernel/heal.cpp`) | OCCT | **no design yet** |
| Topology output (`--topology`, `--edges`) | OCCT | to decide |
| Sandboxed kernel process (Landlock/seccomp/Seatbelt) | needed because OCCT is C++ on untrusted input | to decide: is it still needed for a memory-safe Rust parser? |

## Proposal (for review, not decided)
1. **OCCT stays as the test oracle.** Every gate (G4 containment, the M4a Hausdorff gate, G7 colour parity) compares against OCCT in CI and in `just fastpath-corpus`. The runtime loses OCCT; the test harness keeps it.
2. **The exit criterion is measured.** OCCT leaves the default runtime when the Rust path meshes ≥ 99.x% of corpus faces within the gates and the healing cases are covered. Until then it's an optional feature (`--features occt`) used for routed faces.
3. **Performance:** rayon over products and faces, SIMD in the evaluation kernels, with benches against the scalar baseline and against OCCT's 42 s full view of Ultimaker.
4. **Clean room:** derive everything from the maths and the standards (ISO 10303-42 and Part 21). Never read or translate OCCT source (LGPL; ADR-0001 §4).

## Open questions
- Healing: which repairs does the corpus actually need? Measure first: how many faces fail without `heal.cpp`'s steps?
- Does the sandbox stay once the runtime is pure Rust (defence in depth), or is a memory cap enough?
- Topology output: keep the format, produced from the graph?

## Acceptance (for the ADR)
- `docs/adr/0002-*.md` accepted.
- A healing census on the corpus.
- An exit criterion with numbers.
- An ordered slice plan in this milestone.

Refs: #115, #170, #171, #172

# [Comment #1]() by [gerchowl]()

_Posted on November 15, 2026 at 08:10 PM_

**Owner (2026-11-15): step by step, always compared with OCCT's output as the golden reference.**

What this fixes for the ADR:
1. **Incremental.** One surface type or job per slice, each behind its own gate. OCCT keeps doing whatever Rust doesn't cover yet. There's no big-bang switch.
2. **OCCT is the golden oracle for every slice.** A Rust result is accepted only when it matches OCCT's within the slice's gate:
   - trees and placements: exact or 1e-9;
   - boxes: contain OCCT's mesh points;
   - meshes: sampled Hausdorff ≤ 2·d;
   - colours: equal.
   A Rust result that differs from OCCT is a failing test, never a silent default.
3. **Two forms of the oracle:**
   - **live:** CI and `just fastpath-corpus` run OCCT beside Rust on the corpus, as G3, G4 and M4a do now;
   - **committed golden files:** OCCT-generated reference outputs under `tests/golden/`, regenerated by an explicit `just golden-occt`, so tests still run where OCCT isn't built, and diffs show up in review.
   OCCT leaves the runtime only. It stays in the dev shell and CI as the oracle for good.
